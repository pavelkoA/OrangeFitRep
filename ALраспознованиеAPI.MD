# Aether Lab — API распознавания файлов

Руководство для интеграции • PDF и структурированные данные документов

Описание подготовлено по исходному коду ветки `master`, коммит `845c74214591`. Доступность production и соответствие установленной версии этому коду не проверялись. Примеры ответов иллюстративные; идентификаторы и токены — условные.

## 1. Назначение и схема работы

API принимает ранее загруженные файлы и запускает асинхронную задачу. Обработка включает OCR (извлечение текста), подбор или создание шаблона и структурирование документа языковой моделью. Результат содержит исходный распознанный текст и JSON по схеме шаблона.

```text
Загрузка файла → ID файла → Создание задачи → Опрос статуса
                                          → Текст + JSON-результат
```

Базовый адрес из конфигурации развёртывания: https://aether-lab.ru. Все приведённые пути относительны к нему; завершающий слеш следует сохранять. Это API для авторизованного клиента, не анонимный доступ. Отдельный публичный синхронный метод «PDF → текст» в исследованных маршрутах не найден.

## 2. Авторизация

| Контур | Способ доступа |
| --- | --- |
| `/api/recognition/` | JWT: `Authorization: Bearer <access_token>`, либо сессия Django. |
| `/api/file-manager/` | `X-Billing-Token: <billing_token>`, либо `Authorization: Billing <billing_token>`, либо сессия Django. JWT здесь не подключён. |

Для сквозного сценария используйте billing token для загрузки и JWT для распознавания одного пользователя, либо одну авторизованную сессию. При сессионной авторизации изменяющие запросы требуют CSRF. Billing token — не JWT; не подставляйте JWT в заголовок `X-Billing-Token`.

```http
POST /api/token/
Content-Type: application/json

{"username":"<username>","password":"<password>"}
```

Стандартный ответ SimpleJWT:

```json
{"access":"<access_token>","refresh":"<refresh_token>"}
```

```http
POST /api/token/refresh/
Content-Type: application/json

{"refresh":"<refresh_token>"}
```

Ответ:

```json
{"access":"<new_access_token>"}
```

По production-настройкам репозитория access token действует 1 час, refresh token — 1 сутки. Храните токены вне кода и логов; передавайте только по HTTPS. У billing token должен быть активный расчётный аккаунт или активное корпоративное членство.

## 3. Справочник методов

| Метод | Путь | Назначение |
| --- | --- | --- |
| POST | `/api/file-manager/files/` | Загрузить файл → 201 |
| GET | `/api/file-manager/files/` | Список собственных файлов → 200 |
| GET | `/api/file-manager/files/{id}/` | Карточка собственного файла → 200 |
| GET | `/api/file-manager/files/{id}/download/` | Скачать исходный файл |
| POST | `/api/recognition/tasks/` | Создать задачу → 201 |
| GET | `/api/recognition/tasks/` | Список собственных задач → 200 |
| GET | `/api/recognition/tasks/{id}/` | Статус, текст и JSON → 200 |
| POST | `/api/recognition/templates/` | Создать шаблон по примерам → 201 |
| GET | `/api/recognition/templates/` | Список шаблонов → 200 |
| GET | `/api/recognition/templates/{id}/` | JSON Schema и примеры → 200 |

DELETE на detail-маршрутах файлов, задач и шаблонов возвращает 204. Удаление файла удаляет и физический файл; удаление записи задачи не является подтверждённым способом отменить фоновую обработку. Не используйте PUT/PATCH как контракт обновления: для задач и шаблонов update не реализован, для файлов поля ответа только для чтения.

## 4. Загрузка файла

`POST /api/file-manager/files/`. Рекомендуемый тип тела — `multipart/form-data`. Поле `file` обязательно; `filename` — необязательное имя файла, `name` — отображаемое имя, `content` — необязательный текст у записи файла (не входной OCR-текст задачи).

```bash
curl --fail-with-body -sS \
  "https://aether-lab.ru/api/file-manager/files/" \
  -H "X-Billing-Token: BILLING_TOKEN" \
  -F "file=@./document.pdf;type=application/pdf" \
  -F "filename=document.pdf" \
  -F "name=Документ.pdf"
```

Также принимается JSON с чистой base64-строкой. Передавайте `filename` с расширением `.pdf`; без него генерируется имя без расширения. Формат `data:application/pdf;base64,...` отдельно не поддерживается.

```json
{
  "file": "<base64 PDF без префикса data:>",
  "filename": "document.pdf",
  "name": "Документ.pdf"
}
```

Ответ 201 содержит объект файла:

```json
{
  "id": 123,
  "name": "Документ.pdf",
  "download_url": "<URL хранилища>",
  "is_image": false,
  "author": 42,
  "created": "<datetime>",
  "updated": "<datetime>"
}
```

Сохраните `id` для создания задачи. `download_url` зависит от хранилища; формат и срок действия здесь не фиксированы. Защищённое скачивание: `GET /api/file-manager/files/123/download/` с авторизацией file-manager.

## 5. Создание задачи

```http
POST /api/recognition/tasks/
Authorization: Bearer <access_token>
Content-Type: application/json

{"files":[123],"template_id":7}
```

| Поле | Тип | Правило |
| --- | --- | --- |
| `files` | integer[] | Обязательно. ID предварительно загруженных файлов. Передавайте непустой массив своих файлов. |
| `template_id` | integer | Необязательно. ID готового шаблона; без него сервис подбирает или создаёт шаблон. |

Успешный ответ — 201 с детальным объектом задачи, а не 202. Запрос не ждёт завершения обработки. Параметры `language`, `pages`, `dpi`, `ocr_only`, `callback_url`, удалённый URL файла в этом контракте не объявлены.

```json
{
  "id": 456,
  "template": null,
  "created_at": "<datetime>",
  "status": "PENDING",
  "status_display": {"id":"PENDING","name":"Ожидает"},
  "errors": null,
  "updated_at": "<datetime>",
  "name": "<название задачи>",
  "current_state": null,
  "completion_percentage": 0,
  "raw_data": null,
  "result_data": null,
  "files": [{"id":123,"name":"Документ.pdf", "...":"..."}]
}
```

## 6. Статусы и получение результата

```http
GET /api/recognition/tasks/456/
Authorization: Bearer <access_token>
```

| Статус | Значение |
| --- | --- |
| `PENDING` | Ожидает запуска; возможен возврат в ожидание при ограничении OCR. |
| `RUNNING` | Фоновая обработка выполняется. |
| `DONE` | Пайплайн завершён. Проверяйте фактическое наличие результата. |
| `ERROR` | Обработка завершилась ошибкой. Проверяйте `errors` и `current_state`. |

| Поле | Смысл |
| --- | --- |
| `raw_data` | Распознанный текст, объединённый из страниц/файлов через два перевода строки. |
| `result_data` | JSON структурированных данных. Состав зависит от `json_schema` шаблона; универсальная фиксированная схема реквизитов не задана. |
| `template` | Краткий объект: `id`, `name`, `description`, `created_at`, `updated_at`; либо null. |
| `files` | Массив объектов исходных файлов, как в ответе загрузки. |
| `current_state` | Человекочитаемый этап. Не используйте как стабильный машинный код. |
| `completion_percentage` | Целое число прогресса; не гарантирует готовность или монотонность. |
| `errors` | Текст проблем либо null; может присутствовать и при `DONE`. |

Рекомендуемый клиентский алгоритм: сохранить ID → повторять GET с паузой (например, 3–5 секунд; это рекомендация, не лимит API) → на `DONE` проверить `raw_data`, `result_data` и `errors` → на `ERROR` показать диагностическое сообщение. Установите собственный предел ожидания: некоторые отрицательные сценарии могут оставлять `RUNNING`.

Отдельные координаты текста, confidence, список результатов по страницам и ID операции OCR-провайдера в этом ответе не предусмотрены. Подтверждённого webhook, внешнего cancel/retry и гарантии срока выполнения нет.

## 7. Шаблоны распознавания

```http
POST /api/recognition/templates/
Authorization: Bearer <access_token>
Content-Type: application/json

{"files":[123],"description":"Счета поставщиков"}
```

`files` — обязательный массив ID файлов-примеров; `description` необязательно, допускает пустую строку. Шаблон создаётся с временным именем; JSON Schema строится асинхронно. Отдельного статуса готовности нет. Перед использованием проверяйте `json_schema` через GET detail: шаблон без схемы приводит к ошибке задачи.

```json
{
  "id": 7,
  "name": "<название шаблона>",
  "description": "Счета поставщиков",
  "created_at": "<datetime>",
  "updated_at": "<datetime>",
  "json_schema": {"<схема конкретного документа>": "..."},
  "file_examples": []
}
```

## 8. Списки и пагинация

Списки файлов, задач и шаблонов используют постраничную выдачу по 20 записей: `?page=2`. В списке задач нет `raw_data`, `result_data` и `files` — за результатом обращайтесь к detail. Задачи и шаблоны по умолчанию сортируются по убыванию даты создания.

```json
{
  "count": 25,
  "next": "<URL следующей страницы>",
  "previous": null,
  "results": []
}
```

## 9. Ошибки

Разделяйте ошибку HTTP при создании запроса и ошибку фоновой обработки после успешного 201. Для обработанных ошибок DRF сервис использует следующую оболочку; `details` может отсутствовать:

```json
{
  "error": "<сообщение>",
  "message": "<сообщение>",
  "code": "<код ошибки>",
  "details": "<дополнительные сведения>"
}
```

| HTTP | Типичные причины |
| --- | --- |
| 400 | Обязательное поле не передано, неверный тип данных, ошибка base64. |
| 401 / 403 | Неверная или отсутствующая авторизация. Для recognition возможен 403 из-за порядка auth-классов; для file-manager обычно 401. |
| 403 | CSRF при сессии либо недостаточные права. |
| 404 | Файл/задача отсутствует или не видна текущему пользователю. |
| 405 / 415 | Неподдерживаемый метод / тип тела запроса. |
| 413 | Тело запроса превышает инфраструктурный лимит; JSON-ответ не гарантирован. |
| 500 | Внутренняя ошибка, в том числе при несуществующем ID файла. |

После 201 ошибки OCR/структурирования отражаются в `status`, `errors` и `current_state`. `errors` — свободный текст, не перечисление стабильных кодов. Ограничение запросов OCR-провайдера обрабатывается в фоне с повторными попытками и не означает HTTP 429 при создании задачи.

## 10. Ограничения и особенности реализации

- Основной документированный сценарий этого руководства — PDF. В коде есть ветка OCR изображений, но полная матрица форматов не подтверждена. MIME определяется по расширению; PDF без правильного расширения не считается гарантированно валидным входом.
- В просмотренных сериализаторах нет явного предела размера PDF, количества страниц или числа файлов. Это не обещание обработки файлов любого размера. Реальные пределы OCR-провайдера и рабочий лимит сервиса отдельно не подтверждены.
- Поддержка PDF с паролем, повреждённых PDF и конкретные требования к качеству скана не подтверждены. Обработка читает файл целиком; для интеграции начинайте с небольших корректных PDF.
- При отсутствии файлов либо распознанного текста статус в некоторых ветках остаётся `RUNNING`. `DONE` не гарантирует непустой `result_data` и отсутствие `errors`. Проверяйте статус вместе с данными и собственным timeout.
- Повторный POST не имеет подтверждённого ключа идемпотентности и может создавать дубликаты. Не повторяйте запрос на создание вслепую после сетевого сбоя.
- Списки файлов и задач ограничены текущим пользователем. Шаблоны в исследованном коде не фильтруются по автору; проверки принадлежности переданных ID при создании не полностью реализованы. Используйте только свои файлы и согласованные шаблоны; эти особенности не являются разрешением доступа к чужим данным.
- Создание задачи API само по себе не является подтверждённым контрактом записи документа в 1С. Оно возвращает результаты распознавания; перенос в учётную систему — отдельный сценарий.

## 11. Сквозной пример curl

Требуется curl и jq. `BILLING_TOKEN` и `ACCESS_TOKEN` заранее задайте безопасным способом; не сохраняйте реальные значения в примере. Оба токена должны представлять одного пользователя.

```bash
BASE="https://aether-lab.ru"
UPLOAD=(curl --fail-with-body -sS \
  "BASE/api/file-manager/files/" \
  -H "X-Billing-Token: BILLING_TOKEN" \
  -F "file=@./document.pdf;type=application/pdf" \
  -F "filename=document.pdf")
FILE_ID=(printf "%s" "UPLOAD" | jq -er ".id")
TASK=(curl --fail-with-body -sS \
  "BASE/api/recognition/tasks/" \
  -H "Authorization: Bearer ACCESS_TOKEN" \
  -H "Content-Type: application/json" \
  --data "(jq -nc --argjson id "FILE_ID" '{files:[id]}')")
TASK_ID=(printf "%s" "TASK" | jq -er ".id")
# Повторяйте GET с паузой и собственным пределом ожидания.
curl --fail-with-body -sS \
  "BASE/api/recognition/tasks/TASK_ID/" \
  -H "Authorization: Bearer ACCESS_TOKEN" | \
  jq '{status,current_state,errors,raw_data,result_data}'
```

## 12. Источники и интерактивная документация

Описание основано на коде, а не на выполненном запросе к production. В базе знаний подтверждено существование Консоли распознавания, но точный API-контракт в ней отсутствует. Внутренние инструменты агентного OCR и API OCR-провайдера не являются внешними REST-методами Aether Lab и здесь не описываются как клиентский контракт.

Интерактивные страницы: https://aether-lab.ru/api/recognition/swagger/ и `/api/recognition/redoc/` — требуют авторизацию. `/api/file-manager/redoc/` — для администратора.

- `coder/urls.py`; `coder/settings.py` — маршруты, JWT, пагинация.
- `recognition_service/urls.py`; `views.py`; `serializers.py`; `choices.py`; `models.py` — HTTP-контракт и данные.
- `recognition_service/tasks.py`; `tools.py`; `agent.py` — фоновая обработка, статусы, результаты.
- `file_manager/urls.py`; `views.py`; `serializers.py` — загрузка и скачивание.
- `billing/authentication.py`; `coder/exception_handler.py` — billing token и ошибки.
- `prod/nginx/django_app.conf` — базовый адрес развёртывания.
